# Dart 控制系统整体架构说明

本文档说明当前工程的任务划分、任务间通信、状态机、可替换换弹机构、芯片移植边界、
复位恢复流程以及后续新增功能的修改位置。本文档以当前工作区代码为准，后续修改代码时
应同步更新本文件中的接口、主题和状态说明。

## 一、总体结论

当前工程不需要直接移植完整 PX4 uORB。

本工程已经采用了一个面向当前资源约束的轻量版 uORB 思路：

1. 状态型数据使用固定类型的“最新值主题”；
2. 每个消费者拥有独立的 `topic_subscriber_t` 游标；
3. 消费者只读取自己尚未处理的最新快照，中间旧样本可以被覆盖；
4. 复位、发射、确认、故障和参数更新使用可靠事件队列，按 FIFO 顺序逐条处理；
5. 所有存储均为静态分配，不引入堆分配、动态主题注册或复杂发布线程。

这满足当前系统真正需要的两种通信语义，同时保留了以后扩展为更完整消息总线的边界：

| 数据类型 | 应使用的通信方式 | 是否允许丢弃中间数据 | 当前例子 |
| --- | --- | --- | --- |
| 当前状态、反馈、视觉目标 | 最新值主题 + 消费者订阅游标 | 允许 | 视觉目标、裁判状态、Dart 状态 |
| 必须逐条执行的动作 | 可靠事件队列 | 不允许主动覆盖 | 复位、发射、故障确认、中止 |
| 参数整体更新 | 最新值主题 + 参数更新事件 | 更新请求不能丢 | 参数保存请求、参数快照 |

因此，当前通信方案可以称为“静态 typed topic bus”，而不是完整 PX4 uORB。它保留了
uORB 最有价值的发布者/消费者解耦模型，但不引入 PX4 的多进程运行时、动态元数据、
日志回放、跨进程共享内存和复杂构建依赖。

## 二、分层结构

```text
┌─────────────────────────────────────────────────────────────┐
│ 输入与输出适配层                                             │
│ DecodeTask / UsbTask / Referee / operator_interface          │
└──────────────────────────────┬──────────────────────────────┘
                               │ 发布最新值或可靠事件
┌──────────────────────────────▼──────────────────────────────┐
│ 静态 Topic Bus                                               │
│ 最新值主题：快照 + generation + 消费者游标                   │

└──────────────────────────────┬──────────────────────────────┘
                               │ DartTask 消费

│ dart_runtime                                                 │

                               │
              ┌────────────────▼────────────────┐
              │ dart_sm                         │
              │ 四发业务、瞄准、许可、故障、恢复 │

              ┌────────────────▼────────────────┐
              │ dart_reload_strategy             │
              │ 换弹流程、推板、舵机门协调       │
              └───────────────┬─────────────────┘

              ┌───────────────▼─────────────────┐

       ┌──────────────────────▼──────────────────────┐
       │ dart_platform_ops                           │
```

代码目录职责如下：

| 目录或文件 | 职责 | 修改原则 |
| --- | --- | --- |
| `application/framework/app_tasks.c` | 四个业务任务的静态注册表 | 新增任务只能在此登记栈、TCB、句柄和优先级 |
| `application/framework/topic_bus.*` | 最新值主题、消费者游标、可靠事件队列 | 不在业务文件中直接使用 FreeRTOS 队列 |
| `application/framework/dart_topics.h` | 跨模块数据模型 | 不放 HAL 句柄、动态指针和变长数组 |
| `application/A_Dart/dart_runtime.c` | DartTask 装配和 1 ms 主循环 | 不写具体机械步骤 |
| `application/A_Dart/dart_sm.c` | 发射业务状态机 | 不写 CAN ID、转盘角度和具体舵机协议 |
| `application/A_Dart/loader/` | 换弹策略和可替换机构驱动 | 新机构优先在此扩展 |
| `application/A_Dart/dart_platform.h` | 芯片无关的平台操作表 | 移植芯片时保持上层接口不变 |
| `application/A_Dart/dart_platform_stm32.c` | F427 平台操作表绑定 | 允许访问 HAL 和旧硬件适配层 |
| `application/ARCHITECTURE.md` | 架构和扩展规则 | 接口或任务边界变化时同步更新 |

## 三、任务划分与所有权

当前只保留四个业务任务：

### 1. DartTask

文件入口为 `dart_task()`，实际运行循环为 `dart_runtime_task()`。

主要职责：

- 以 1 ms 周期采集平台反馈；
- 通过消费者订阅接口读取视觉、裁判和参数最新快照；
- 按 FIFO 消费 Dart 命令事件；
- 推进 `dart_sm` 状态机和当前换弹策略；
- 将抽象执行器命令交给平台层；
- 运行旧电机/PID 兼容层；
- 发布 `DART_FEEDBACK`、`DART_STATUS` 和故障事件。

DartTask 是以下运行态的唯一业务所有者：

- 当前顶层状态和子状态；
- 四发计数 `shot_index`；
- 当前目标、发射许可和瞄准稳定计时；
- 恢复进度和故障锁存状态；
- 当前周期执行器目标。

其他任务不得直接修改上述字段，也不得绕过 `dart_sm_command()` 控制执行器。

### 2. DecodeTask

主要职责：

- 在任务上下文解析 USB 视觉帧和裁判串口帧；
- 中断中只复制数据、发送通知，不执行 CRC 和业务解析；
- 视觉帧通过 `TOPIC_VISION_TARGET` 发布最新目标；
- 裁判帧通过 `TOPIC_REFEREE_STATUS` 发布最新状态。

视觉数据不进入可靠队列。视觉数据具有强时效性，DartTask 如果一段时间没有运行，恢复
后应该使用当前最新目标，而不是依次处理已经过期的旧目标。

### 3. UsbTask

主要职责：

- 只初始化一次 USB 设备栈；
- 从静态发送队列中读取完整帧；
- 根据每条队列元素保存的实际长度发送数据；
- 处理 CDC 端点暂时忙的重试。

业务模块不得直接调用 USB CDC 发送函数，应通过 `usb_tx_enqueue()` 或协议封装函数入队。

### 4. AdjustTask

主要职责：

- 从 Flash 读取完整参数块；
- 检查魔数、版本、尺寸、CRC、浮点值和安全范围；
- 无效时使用安全默认参数；
- 串行处理参数更新事件并写回 Flash；
- 只有保存成功后才发布新参数快照。

参数更新不是逐字段修改。DartTask 只在 BOOT、STANDBY 或 FAULT_LATCHED 等安全边界整体
替换参数，避免机械动作过程中出现一半旧参数、一半新参数。

## 四、任务间通信设计

### 4.1 最新值主题

最新值主题由静态存储对象和发布代数组成。发布时完整复制结构，再递增 generation；读取
者使用自己的 `topic_subscriber_t` 保存消费进度。

当前主题如下：

| 主题 | 发布者 | 当前消费者 | 语义 |
| --- | --- | --- | --- |
| `TOPIC_VISION_TARGET` | `DecodeTask` | `DartTask` | 只保留最新视觉目标 |
| `TOPIC_REFEREE_STATUS` | `Referee` / `DecodeTask` | `DartTask` | 只保留最新裁判状态 |
| `TOPIC_DART_FEEDBACK` | `DartTask` | 操作接口、诊断模块 | 最新硬件反馈 |
| `TOPIC_DART_PARAMETERS` | `AdjustTask` 或启动兜底 | `DartTask` | 最新完整参数块 |
| `TOPIC_DART_STATUS` | `DartTask` | 操作接口、诊断模块 | 最新业务状态 |

消费者使用方式：

```c
topic_subscriber_t vision_subscriber;
vision_target_t vision;

topic_subscriber_init(&vision_subscriber);

if (topic_subscriber_read_latest(&vision_subscriber,
                                 TOPIC_VISION_TARGET,
                                 &vision)) {
    /* 只处理当前消费者尚未处理的最新视觉快照。 */
}
```

多个消费者订阅同一主题时，必须各自创建 `topic_subscriber_t`，不能共享一个 generation。
共享游标会导致一个消费者读取后另一个消费者误以为数据已经处理，破坏发布/订阅语义。

### 4.2 可靠事件

可靠事件使用静态 FreeRTOS 队列，按到达顺序逐条保存：

| 事件主题 | 生产者 | 消费者 | 不能使用最新值主题的原因 |
| --- | --- | --- | --- |
| `TOPIC_DART_COMMAND` | 操作员接口、遥控器桥接 | `DartTask` | 复位、中止、确认不能被后来的命令覆盖 |
| `TOPIC_PARAMETER_UPDATE` | 操作员接口 | `AdjustTask` | 每次更新都需要校验、保存和反馈结果 |
| `TOPIC_FAULT_EVENT` | `DartTask` | 诊断或上层 | 故障首次发生需要保留，不能只看当前故障值 |

可靠事件队列满时，接口返回失败。对于命令丢失风险，后续可以增加队列溢出故障或专门的
应答事件，但不能静默改成最新值覆盖。

### 4.3 是否需要完整 PX4 uORB

当前不建议移植完整 PX4 uORB，原因如下：

- 当前所有任务运行在同一个 FreeRTOS 地址空间，不需要跨进程通信；
- 主题数量、数据结构和发布者都固定，静态绑定更容易检查 RAM 和栈占用；
- 当前不需要 uORB 的日志回放、跨进程共享内存、动态消息元数据和多实例管理；
- 视觉和裁判数据明确是最新值语义，静态快照比队列更符合控制需求；
- 复位和动作命令明确是可靠事件，独立静态队列比统一消息机制更容易保证不丢失。

如果以后出现以下需求，再考虑扩展 topic bus，而不是直接把业务层改成 uORB API：

- 主题数量需要运行时动态注册；
- 多个板卡或进程之间需要跨地址空间通信；
- 需要主题日志回放和离线重放；
- 需要多实例同类型传感器的发现和优先级选择；
- 需要统一 QoS、队列深度、时间戳和诊断统计。

在此之前，`topic_subscriber_t` 已经提供了清晰的消费者订阅抽象。

## 五、状态机结构

顶层状态路径如下：

```text
BOOT -> HOMING -> STANDBY
                    ├─> MANUAL
                    └─> PREPARE -> RELOAD -> AIM -> WAIT_LAUNCH -> FIRE
                                      ▲                         │
                                      │                         ▼
                                      └─ POST_SHOT <- WAIT_NEXT_WINDOW
                                                        │
                         第四发完成 -> CYCLE_COMPLETE -> RECOVERING -> STANDBY

任意工作状态 --故障/中止/复位--> RECOVERING 或 FAULT_LATCHED
```

上电 `HOMING` 中，扳机、左右推板组和 Yaw 在同一控制周期启动，各自独立寻找限位并
返回安全位置；左右推板内部仍同步运动并检查两侧限位时间差。三组核心轴全部完成后才
推进可选换弹机构回零。`status.substate` 每两位记录一组进度：位 0～1 为扳机、位 2～3
为推板、位 4～5 为 Yaw，数值 0/1/2 分别表示找限位/回位/已完成；位 6 表示已进入
可选机构步骤。工作中复位与故障恢复仍按原来的严格顺序执行，不与上电回零混用。

状态机的共同规则：

- 每个状态和子步骤只执行一次进入动作；
- 每个动作必须根据真实反馈判断完成，不能仅根据发送命令判断完成；
- 每个动作都有独立超时；
- 超时、反馈离线和同步误差必须进入明确故障出口；
- 恢复不跳步、不自动重试；
- `shot_index` 为零基索引，只在 FIRE 保持时间完整结束后递增；
- 第四发完成后必须经过 `CYCLE_COMPLETE -> RECOVERING`，不能直接回 STANDBY。

## 六、四发循环与发射条件

一次四发循环的业务原则：

1. `PREPARE` 检查目标、发序号和当前机构能力；
2. `RELOAD` 由策略准备指定发次；
3. `AIM` 等待扳机、Yaw 和视觉误差达到要求；
4. `WAIT_LAUNCH` 同时检查操作员发射请求、裁判许可、视觉新鲜度和反馈在线状态；
5. `FIRE` 保持发射机构开启指定时间；
6. 只有 FIRE 完整结束后才增加发数；
7. 第一、三发完成后准备下一发；
8. 第二发完成后进入下一裁判窗口等待；
9. 第四发完成后进入完整恢复。

视觉和裁判快照超过 200 ms 未更新时禁止发射。视觉主题本身只保存最新数据，但每份
快照保留 `timestamp_ms`，因此“只取最新”不会削弱新鲜度保护。

## 七、复位与恢复

### 7.1 业务复位清除内容

完整恢复成功后统一清除：

- 发射计数和当前目标；
- 发射许可、发射请求和瞄准稳定计时；
- 换弹机构当前弹位、步骤、活动舵机门和内部计时；
- 旧命令事件；
- PID 积分、误差、滤波和旧执行器目标。

不清除：

- Flash 中的标定参数；
- 参数版本、机构类型和 CRC；
- 平台硬件资源配置。

### 7.2 安装原换弹机构时的恢复顺序

当前恢复策略严格按以下顺序执行：

1. 禁止发射并让发射机构进入安全状态；
2. 左右升降轴同步到交接高度；
3. DM6006 转盘回到 `loader_turn_position[0]`；
4. 左右推板同步下降到 `push_load_position`，即原 `set_drive_distance()` 对应位置；
5. 打开当前活动舵机门；
6. 左右推板同步返回 `push_back_position`；
7. 执行扳机轴回零；
8. 执行左右推板成对回零；
9. 执行左右升降轴成对回零并离开限位到安全高度；
10. 执行 Yaw 轴回零并回到安全角度；
11. 关闭全部舵机门，清除业务上下文并进入安全待机。

左右推板和左右升降轴都是逻辑成对轴：必须同时启动、同时停止，且两侧都满足位置或
限位条件后才能进入下一步。单侧离线、同步误差超限、单侧限位等待超时或整个步骤超时，
都必须停止成对轴并锁存故障。

### 7.3 当前拆机配置

`DART_ENABLE_CAROUSEL_LOADER` 默认值为 `0`。拆机配置下：

- 原转盘升降 loader 源文件不进入固件；
- 不初始化原舵机总线；
- 主状态机不等待升降轴和 DM6006 反馈；
- 使用 `detached_reload_strategy`，不产生换弹硬件输出；
- 上电回零只处理扳机、左右推板和 Yaw；
- 若 `initial_dart_preloaded=true`，第一发可以直接进入瞄准；
- 后续需要真实换弹时报告 `DART_FAULT_LOADER_UNAVAILABLE` 并禁止发射。

## 八、替换换弹机构

### 8.1 只改变驱动方式，机械流程不变

实现新的 `dart_loader_ops_t`：

- `init()`：检查依赖并初始化，不启动运动；
- `start()`：登记一个非阻塞动作，不等待机构到位；
- `step()`：每个 DartTask 周期推进一次；
- `abort()`：立即撤销该机构拥有的全部输出；
- `get_status()`：按值返回 `IDLE/BUSY/DONE/FAULT`、故障码和步骤号。

此时不修改 `dart_sm.c`，只在 `dart_runtime.c` 完成新的上下文绑定。新机构内部应自己
维护位置、限位、超时、在线状态、同步误差和故障步骤。

### 8.2 机械流程也发生变化

同时实现新的 `dart_reload_strategy_t`。新策略负责：

- 推板与换弹机构的时序；
- 舵机门或夹持机构的时序；
- 机构内部动作的完成条件；
- 受控恢复和中止；
- 失败步骤和故障码。

`dart_sm.c` 只允许看到策略的启动、推进、中止和状态结果，不应出现新机构的电机编号、
弹位角度、GPIO、舵机协议或机械尺寸。

## 九、移植到其他 STM32 芯片

移植时只替换板级资源和平台实现，不修改业务状态机：

1. 新建对应的 `dart_platform_<board>.c`；
2. 实现 `dart_platform_ops_t` 的时间、反馈、输出、回零、参数和通信回调；
3. 将 HAL 句柄、GPIO、CAN 标识符、电机数组和 Flash 地址限制在板级适配层；
4. 将新板级文件加入应用源码白名单；
5. 检查 FreeRTOS 中断优先级、静态栈大小和参数 Flash 擦写区域；
6. 逐轴确认方向、限位极性、编码器零点和成对轴同步阈值；
7. 确认 USB CDC、裁判串口和 CAN 的反馈时间戳都使用同一单调时钟。

业务层禁止直接访问：

- HAL 的 CAN/UART/PWM 句柄；
- GPIO 宏；
- 具体电机数组；
- 具体 CAN ID；
- 旧协议结构体的全局可写实例。

## 十、串口屏预留接口

当前不规定串口帧格式、页面、控件 ID 和 USART1 具体实现。后续串口屏适配器只能调用：

```c
bool operator_command_submit(const dart_command_t *command);
bool operator_status_read(dart_status_t *status);
bool operator_parameters_read(dart_parameters_t *parameters);
bool operator_parameters_update(const parameter_update_t *update);
```

串口屏读取状态和参数时使用最新值语义；提交复位、发射、确认和中止时使用可靠命令事件。
串口屏模块不得直接调用 `dart_sm_*()`、平台 HAL 或换弹机构接口。

## 十一、后续新增内容的修改规则

### 新增一个状态型数据

1. 在 `dart_topics.h` 定义固定长度结构；
2. 在 `topic_bus.h` 增加主题编号；
3. 在 `topic_bus.c` 增加静态存储和绑定；
4. 明确唯一发布者和每个消费者；
5. 消费者各自持有 `topic_subscriber_t`；
6. 在本文档的主题表补充说明；
7. 不为视觉、姿态、反馈等高频状态创建 FIFO 队列，除非确实需要逐样本处理。

### 新增一个不可丢失动作

1. 在 `dart_topics.h` 定义事件结构；
2. 在 `topic_bus.h/.c` 增加事件主题和静态队列；
3. 定义队列满时的处理策略；
4. 由唯一业务所有者按 FIFO 消费；
5. 在恢复边界明确是否清除旧事件；
6. 不把复位、中止、确认等动作改成最新值主题。

### 新增一个任务

只有在确实需要独立阻塞等待或独立实时优先级时才新增任务。新增任务必须：

1. 使用静态栈和静态 TCB；
2. 在 `app_tasks.c` 统一注册；
3. 通过 Topic Bus 或已有抽象接口通信；
4. 不直接修改 Dart 状态机内部数据；
5. 在本文档补充任务职责、输入、输出和优先级原因。

## 十二、当前框架的边界与后续建议

当前框架已经覆盖任务注册、静态通信、最新值消费者、可靠事件、状态机、故障恢复、
可替换换弹机构、拆机编译开关、F427 平台适配和串口屏预留接口。

后续优先级建议：

1. 机构重新安装后，先实现新的 loader 或恢复原 loader，再验证成对轴方向和限位；
2. 为 Topic Bus 增加发布失败、事件队列溢出和主题更新时间统计；
3. 为 Dart 状态机增加统一状态转移日志，记录进入时间、步骤和故障；
4. 根据实际 Flash 磨损要求决定参数双备份、序列号和掉电保护；
5. 只有在出现跨进程、日志回放或动态主题需求时，才重新评估完整 PX4 uORB。
